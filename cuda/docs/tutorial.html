Tutorial · OpenFOAM Foundation v14

OpenFOAM's pressure solver on the GPU with CUDA

A walkthrough tested end to end: build OpenFOAM-14 from scratch, couple NVIDIA's AMGX as the pressure solver through fvSolution, and run a real case on the GPU, without changing a single line of the Foundation source code.

NVIDIA GPU, compute capability ≥ 7.0 WSL2 · Ubuntu 22.04 ~25 GB of free disk
motorBike · 3.2 M cells · the GPU benchmark case
01

Prerequisites

Check the GPU and the distro before starting; it saves rework later.

$ nvidia-smi --query-gpu=name,compute_cap,driver_version --format=csv
# name, compute_cap, driver_version
# NVIDIA GeForce RTX 4050 Laptop GPU, 8.9, 596.08
Important: write down the compute_cap (e.g. 8.9); it becomes sm_89 later. Using the wrong architecture is the most common mistake in this tutorial (§10).
02

CUDA Toolkit (WSL-Ubuntu repository)

Use the specific wsl-ubuntu repository: Ubuntu's generic package tries to install the Linux driver, which conflicts with the Windows driver that already bridges the GPU into WSL.

$ wget https://developer.download.nvidia.com/compute/cuda/repos/wsl-ubuntu/x86_64/cuda-keyring_1.1-1_all.deb
$ sudo dpkg -i cuda-keyring_1.1-1_all.deb
$ sudo apt-get update
$ sudo apt-get install -y cuda-toolkit-13-2
$ export PATH=/usr/local/cuda/bin:$PATH
$ nvcc --version
# Cuda compilation tools, release 13.2, V13.2.86
Careful: if your WSL already has Ubuntu's generic nvidia-cuda-toolkit package (it ships an old nvcc, version 11.5, in /usr/bin/nvcc), it comes first in the PATH. Check with which nvcc: if it points to /usr/bin/nvcc, export the PATH above before any build.
03

Build OpenFOAM-14

The local folder must be called exactly OpenFOAM-<version>: etc/bashrc derives its paths from that name.

$ mkdir -p ~/dev && cd ~/dev
$ git clone https://github.com/ileaof/openFoam-14-cuda.git OpenFOAM-14
$ sudo apt-get install -y build-essential flex bison cmake git \
    zlib1g-dev libboost-system-dev libboost-thread-dev \
    libopenmpi-dev openmpi-bin libreadline-dev libncurses-dev \
    libxt-dev rpm libscotch-dev libptscotch-dev
$ cd ~/dev/OpenFOAM-14
$ source etc/bashrc
$ ./Allwmake -j $(( $(nproc) / 2 ))  # limit RAM use: do not use every core at once
Check that it worked: after the build, ls $FOAM_APPBIN | wc -l should show ~145 binaries (solvers + utilities). Errors in PVReaders/ParaView are expected and harmless if you did not install the visualization libraries.
04

Build AMGX (NVIDIA)

This is the library that does the actual solve on the GPU: an algebraic multigrid in pure CUDA, independent of OpenFOAM. cuda/scripts/build_all.sh does steps 4 to 6 for you; they are shown here so you know what it does.

$ cd ~/dev && git clone --recursive https://github.com/NVIDIA/AMGX.git
$ cd AMGX && mkdir build && cd build
$ cmake -DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc \
        -DCMAKE_CUDA_ARCHITECTURES="89" \
        -DCMAKE_BUILD_TYPE=Release ../
$ make -j4 all  # -j4, not -j$(nproc): avoids running out of WSL RAM
Replace 89 with your GPU's compute_cap, without the dot (8.9 → 89, 7.5 → 75, 8.6 → 86...).

Expected result: build/libamgxsh.so and build/libamgx.a.

05

Build foam2csr

Converts OpenFOAM's LDU matrix to the CSR format AMGX understands. It uses PETSc types internally, only as infrastructure, not to solve anything.

$ sudo apt-get install -y libpetsc-real-dev
$ cd ~/dev && git clone https://github.com/mattmartineau/foam2csr.git

Ubuntu's PETSc package uses different names from the ones the code expects. Fix it with your own symbolic links, without touching the system:

$ mkdir -p ~/dev/compat/lib
$ ln -s /usr/lib/x86_64-linux-gnu/libtrilinos_zoltan.so ~/dev/compat/lib/libzoltan.so
$ ln -s /usr/lib/petscdir/petsc3.15/x86_64-linux-gnu-real/lib/libpetsc_real.so \
        ~/dev/compat/lib/libpetsc.so

Apply this repository's patch at the tested commit (none of it is OpenFOAM Foundation code). It fixes a C-style comment that GNU Make rejects, the hard-coded architecture, the C++ standard and the MPI include:

$ cd ~/dev/foam2csr
$ git checkout eb21649ed8b10d438d047485c0dd62cce33d269f
$ git apply --check ~/dev/OpenFOAM-14/cuda/patches/foam2csr.patch   # dry run
$ git apply ~/dev/OpenFOAM-14/cuda/patches/foam2csr.patch
# the patch sets NVARCH = 89 (RTX 40xx); for another GPU use your compute capability
$ sed -i "s/^NVARCH = .*/NVARCH = 89/" Make/nvcc
$ export AMGX_INC=~/dev/AMGX/include  AMGX_LIB=~/dev/AMGX/build
$ export CUBROOT=/usr/local/cuda/targets/x86_64-linux/include/cccl
$ export PETSC_INC=/usr/lib/petscdir/petsc3.15/x86_64-linux-gnu-real/include
$ export PETSC_LIB_DIR=~/dev/compat/lib
$ ./Allwmake
Expected result: libfoam2csr.so in $FOAM_USER_LIBBIN.
06

Port and build amgx4Foam

This is the wrapper that registers amgx as a real lduMatrix::solver inside OpenFOAM. The fork available in the community was written for an older API and needs these changes to build on v14 (all of them are in cuda/patches/amgx4foam.patch).

$ cd ~/dev && git clone https://github.com/maorz1998/amgx4foam.git
$ cd amgx4foam && git checkout 52dee12055c10d25a37e76291485b8aeb1cd42cf
$ git apply ~/dev/OpenFOAM-14/cuda/patches/amgx4foam.patch

What the patch changes:

$ export FOAM2CSR_INC=~/dev/foam2csr/src
$ export FOAM2CSR_LIB=$FOAM_USER_LIBBIN
$ cd ~/dev/amgx4foam && ./Allwmake
Expected result: libamgxFoam.so in $FOAM_USER_LIBBIN, with no broken dependencies (ldd libamgxFoam.so | grep "not found" should print nothing).
07

Set up a case to use the GPU

Three files in any case. None of them is code: they are just OpenFOAM's own configuration dictionaries.

system/controlDict: load the library:

libs            ("libamgxFoam.so");

system/fvSolution: switch the solver of the p field:

p
{
    solver          amgx;
    amgx
    {
        dict p;
    }
}

system/amgxpOptions: AMGX's native configuration (the name follows the pattern amgx + dict + Options). Copy it from cuda/config/amgxpOptions; its core is:

{
    "config_version": 2,
    "solver": {
        "solver": "FGMRES",
        "preconditioner": { "solver": "AMG", "algorithm": "CLASSICAL", "selector": "PMIS",
                            "structure_reuse_levels": -1, ... },
        "convergence": "RELATIVE_INI",
        "tolerance": 0.1,
        "store_res_history": 1
    }
}
The stopping criterion that counts is the one in this JSON. The tolerance and relTol in fvSolution are ignored by amgx4Foam. Set "tolerance" here to the same value as your relTol (e.g. 0.1), and give pFinal its own dictionary and file for the final corrector. Details in §9.
store_res_history: 1 is mandatory: without it AMGX converges normally but fails when handing the residual back for OpenFOAM to report.
08

Full case: prove the numerics

Before trusting the GPU with a large case, run this: OpenFOAM's standard cavity tutorial, small enough to finish in seconds. The point here is not speed: it is proving that the result matches the CPU reference before trusting anything bigger.

1. Prepare the two cases (same mesh, only the p solver changes):

$ mkdir -p ~/runs && cd ~/runs
$ cp -r $FOAM_TUTORIALS/legacy/incompressible/icoFoam/cavity/cavity cavity_cpu
$ cp -r cavity_cpu cavity_gpu
$ cd cavity_cpu && blockMesh && cd ..

In cavity_gpu, apply the three files from §7 (libs in controlDict, solver amgx; in fvSolution, and system/amgxpOptions), then decompose both into 2 subdomains (numberOfSubdomains 2; + decomposePar). The GPU requires -parallel, so run both cases the same way for a fair comparison.

2. Run both:

$ cd ~/runs/cavity_cpu && mpirun -np 2 icoFoam -parallel
$ cd ~/runs/cavity_gpu && mpirun -np 2 icoFoam -parallel
AMGx:  Solving for p, Initial residual = 1.40477e-15, Final residual = 5.2475e-19, No Iterations 28
time step continuity errors : sum local = 1.56388e-16, global = -3.53206e-20
ExecutionTime = 9.5838 s  ClockTime = 9 s
That's it: the line starting with AMGx: (instead of DICPCG:) confirms that the pressure solve ran on the GPU.

3. Compare the final pressure field. This is the proof:

$ reconstructPar -case cavity_cpu && reconstructPar -case cavity_gpu
$ diff cavity_cpu/0.5/p cavity_gpu/0.5/p | head
BuildFinal p residualResult
GCC, CPU (DICPCG)8.638e-07reference
Intel oneAPI, CPU (DICPCG)8.638e-07identical to GCC, bit for bit
AMGX, GPU (PCG+AMG)5.248e-19converged; final field within ~1e-4 of the CPU

The diff will not be empty, and it should not be. Different iterative methods (AMG vs. DIC) converge to the same physics along different paths, both within the configured tolerance (1e-6). What matters is the order of magnitude of the difference, not zero.

Only after this is it worth moving to a large case. For speed, use tutorials/GPU/cavity3D (transient, 0.5 to 3.4 M cells), where the GPU is 1.42× faster at 1 M cells and 2.09× at 3.4 M. See the numbers in the technical report and in cuda/benchmarks/.
09

Before giving up on the GPU

With a naive configuration, the GPU can end up slower than the CPU, or crash mid-run. Every item below actually happened during the tests for this tutorial, with the measured number. None of them means the GPU is useless: it means it was used outside the conditions where it pays off.

PitfallWhat we measuredHow to avoid it
fvSolution tolerance ignored motorBike: with relTol 0.1 in fvSolution, GAMG on the CPU stopped after 2 iterations per solve. AMGX took 41 iterations and went down to a residual of 2e-08, because it followed the JSON criterion (1e-6 reduction). The amgx4Foam and foam2csr code reads neither tolerance nor relTol. Put the stopping criterion in amgxpOptions: "convergence": "RELATIVE_INI" with "tolerance": 0.1 reproduces relTol 0.1. Without it the GPU does much more work than the CPU and the comparison is unfair.
Small mesh cavity, 40 k cells, 10 steps: CPU 2.3 s vs. GPU 6.4 s The fixed cost of setting up the problem on the GPU dominates on small meshes. Judge the GPU only on large meshes (hundreds of thousands of cells and up). Use the cavity only to validate the result, never to measure speed.
Rebuilding the AMG every iteration On the cavity, setup was already 38% of each solve. With reuse turned on, the motorBike setup dropped from 0.49 s to 0.15 s per solve. Add "structure_reuse_levels": -1 to the preconditioner block of amgxpOptions (already in the repository file). The matrix is still updated every iteration; only the multigrid hierarchy pattern is reused.
amgx4Foam periodic cache From the code: in this mode the matrix stops being updated in the intermediate iterations, not just the preconditioner. Do not use periodic, adaptive or never. The GPU would solve the pressure from an earlier iteration and the result would be physically wrong, even though it converges. Keep update always; (the default) and use the reuse from the row above.
The wrong AMGX recipe cavity3D, 1 M cells: PCG_AGGREGATION_JACOBI took 22.8 iterations and 0.766 s/step, slower than the CPU (0.575 s). FGMRES_CLASSICAL_AGGRESSIVE_PMIS: 5.5 iterations, 0.417 s/step. Use the repository default (PMIS) and compare recipes on your own case with cuda/scripts/tune_amgx.py.
Too many MPI ranks on a single GPU With 8 ranks, each opens its own CUDA context on the same 6 GB card, and takes host RAM too. Start with 2 to 4 ranks per GPU. More ranks help the part that runs on the CPU, but compete for the card's memory.
Other programs using the GPU motorBike crashed at iteration 289 of 500 with Cuda failure: 'unknown error' and Out of resource. AMGX was stable at 3.0 GB; ParaView and the Windows desktop held the rest of the card. Close ParaView, games and heavy browser tabs before a long run. On a laptop, the same GPU also draws the screen. Check free memory with nvidia-smi before starting.
WSL2 memory With 12 of 15.7 GB given to WSL, Windows was left with 0.1 GB free and restarted the virtual machine, killing a build in progress. Long runs also grow WSL's page cache, which is not returned to Windows. Leave at least half of the RAM to Windows in .wslconfig (e.g. memory=8GB on a 16 GB machine), build with make -j4, close other programs, and run wsl --shutdown between long runs to free the cache.

What to expect: measured on the motorBike

3.2 M cells, 4 ranks, foamRun with incompressibleFluid (SIMPLE), average time of iterations 10 to 100.

Configurations / iterationp solver iterationsCd (it. 100)
First attempt: GPU with the JSON tolerance (1e-6), 8 ranks3.741—
CPU, GAMG2.5502.00.7210
GPU, matched tolerance (0.1)2.5221.40.7214
GPU, matched tolerance + AMG reuse2.4781.40.7200

With the right configuration, the GPU ties with the CPU and the physical result is the same. It does not pull far ahead because, in this case, the pressure solve is only 0.26 s of each 2.48 s iteration (about 10%). The other 90% are the velocity and turbulence equations, matrix assembly and post-processing, which stay on the CPU. Even with an instant pressure solve, the most one could gain is ~12%.

Where the GPU pays off: in cases where the pressure solve dominates the iteration. That happens in transient flows (PISO/PIMPLE) with several pressure correctors and pFinal with a tight relTol, on large meshes. On the cavity3D the GPU goes from 1.03× at 0.5 M cells to 2.09× at 3.4 M. Before investing in a case, look at the CPU log: if GAMG takes only 1 to 3 iterations per solve, the pressure is already cheap and the GPU has little to gain.
Rule of thumb: validate the result on the cavity (§8), measure performance on a large case, match the JSON tolerance to relTol, use the PMIS recipe and 2 to 4 ranks, reuse the AMG structure and keep the GPU free during the run. Only then compare with the CPU.

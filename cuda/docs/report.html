Accelerating OpenFOAM Foundation v14 with a GPU

A fork of OpenFOAM-14 with the pressure solver running in CUDA through AMGX, without any change to the Foundation source code. This document is the technical record of how it was built, what broke, and the validation and performance numbers so far.

Fix log

None of them touches the OpenFOAM Foundation: they are all in third-party code (the three projects above), mostly because it was written for a different version of OpenFOAM or CUDA.

C-style comment in a Makefile

/* Failsafe */ in Make/options: GNU Make only understands #. It broke with missing separator.

Fix: replaced with # in the three modules.

Wrong CUDA architecture

foam2csr had NVARCH = 70 (Volta) hard-coded, incompatible with the RTX 4050.

nvcc fatal : Unsupported gpu architecture 'compute_70'
Fix: NVARCH set from the GPU's compute capability by build_all.sh (89 for Ada Lovelace).

Missing MPI include

Make/options did not inherit $(PFLAGS) $(PINC), so mpi.h was not found.

Fix: added at the start of EXE_INC.

C++17 required by CUDA 13.2

The CUB/Thrust bundled with CUDA 13.2 (CCCL) needs C++17; the build used -std=c++14.

error: CUB requires at least C++17.
error: libcu++ requires at least C++ 17.
Fix: -std=c++17 in foam2csr's wmake rule.

Mismatched library names (Debian packaging)

Three dependencies, same pattern: the code expects one name, the Ubuntu package installs another.

ExpectedActual
libzoltan.solibtrilinos_zoltan.so
libpetsc.solibpetsc_real.so
libfoam_csr.solibfoam2csr.so
Fix: compatibility symbolic links in a folder of their own: zero changes to the system or to OpenFOAM.

CUDA path pinned to an old version

-I/usr/local/cuda-11.6/include hard-coded in the amgx4Foam wrapper.

Fix: changed to /usr/local/cuda (a symlink to the active version).

MeshObject renamed in v14

OpenFOAM-14 replaced MeshObject<Mesh,Tag,Type> with DemandDrivenMeshObject, with different tag categories (TopoChangeableMeshObject requires 4 pure virtual methods our class does not need).

Fix: moved to DemandDrivenMeshObject with the DeletableMeshObject tag (no pure virtuals: the class only needs to be recreated when the mesh changes).

Header removed in v14

cyclicAMILduInterface.H no longer exists, and it was not actually used by any function.

Fix: #include removed.

thisDb() → db()

Method renamed in v14's lduMesh interface.

Fix: replaced in both occurrences.

PETSc was never initialized

foam2csr uses PETSc types internally, but nothing on the execution path called PetscInitialize: the original code relied on another component (removed in this fork) for that.

Signal: Segmentation fault (11)
 #7 PetscVFPrintfDefault
 #8 AmgXSolver::setDeviceCount()
Fix: PetscInitializeNoArguments() guarded by PetscInitialized(), in the context constructor.

Residual history not recorded

AMGX only lets you query the residual after the solve if store_res_history is on, and it was not in the initial configuration JSON.

Fix: "store_res_history": 1 in the main solver config.

MPI not initialized in a serial run

Running icoFoam without mpirun never initializes MPI, but AMGX calls MPI functions unconditionally.

Fix: not a bug, a requirement: this kind of solver always runs through mpirun -np N icoFoam -parallel (N ≥ 2).

const-correctness

const double* passed where foam2csr's API expects a non-const PetscScalar*.

Fix: const_cast<double*> at the call site (the value is not actually modified).

Validation

cavity case (moving lid, icoFoam solver): same mesh, three compiler/solver configurations.

BuildFinal p residualResult
GCC (CPU, DICPCG)8.638e-07reference
Intel oneAPI (CPU, DICPCG)8.638e-07identical to GCC
AMGX (GPU, PCG+AMG)5.248e-19converged, final field within ~1e-4 of the CPU

GCC and Intel produce a bit-for-bit identical pressure field. The GPU converges to the same physics with an expected residual difference: different iterative methods (aggregation-based preconditioner vs. DIC), same target tolerance (1e-6).

10 time steps. The CPU won here: at this scale, the overhead of setting up the AMGX/CUDA context outweighs the gain in the solve itself. The GPU only pays off on much larger meshes and with the AMG structure reused between iterations.

motorBike: 3.2 million cells

External aerodynamics, foamRun with incompressibleFluid (SIMPLE, steady state). Average time per iteration between iterations 10 and 100, 4 MPI ranks.

GPU, 1st attempt
3.7 s
CPU, GAMG
2.55 s
GPU, matched tol.
2.52 s
GPU, tol. + AMG reuse
2.48 s
The 1st attempt (8 ranks) looked 50% slower, but the cause was configuration: amgx4Foam ignores the relTol 0.1 in fvSolution and AMGX solved down to the JSON tolerance (1e-6), with 41 iterations per solve against 2 for GAMG. With the tolerance matched, the three runs reach the same Cd (0.720 to 0.721).

Why the GPU only ties here. The AMGX pressure solve takes 0.26 s of each 2.48 s iteration, about 10%. The other 90% are velocity, turbulence, matrix assembly and post-processing, which stay on the CPU. Even with an instant pressure solve, the most one could gain is ~12%.

The GPU pays off when the pressure dominates the iteration: transient cases (PISO/PIMPLE) with several correctors and a tight pFinal, as the cavity3D above shows.

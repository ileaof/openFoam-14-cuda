Acelerando o OpenFOAM Foundation v14 com GPU

Um fork do OpenFOAM-14 com o solver de pressão rodando em CUDA via AMGX, sem nenhuma alteração no código-fonte do Foundation. Este documento é o registro técnico de como foi construído, o que quebrou, e os números de validação até agora.

Log de correções

Nenhuma delas toca no OpenFOAM Foundation — são todas em código de terceiros (os três projetos acima), a maioria porque foram escritos para uma versão diferente do OpenFOAM ou do CUDA.

Comentário em estilo C num Makefile

/* Failsafe */ em Make/options — GNU Make só entende #. Quebrava com missing separator.

Correção: trocado por # nos três módulos.

Arquitetura CUDA errada

foam2csr tinha NVARCH = 70 (Volta) fixo no código — incompatível com a RTX 4050.

nvcc fatal : Unsupported gpu architecture 'compute_70'
Correção: NVARCH = 89 (Ada Lovelace).

Include do MPI faltando

Make/options não herdava $(PFLAGS) $(PINC), então mpi.h não era encontrado.

Correção: adicionado ao início de EXE_INC.

C++17 exigido pelo CUDA 13.2

O CUB/Thrust empacotado no CUDA 13.2 (CCCL) exige C++17 — o build usava -std=c++14.

error: CUB requires at least C++17.
error: libcu++ requires at least C++ 17.
Correção: -std=c++17 no wmake rule do foam2csr.

Nomes de bibliotecas trocados (empacotamento Debian)

Três dependências, mesmo padrão: o código espera um nome, o pacote Ubuntu instala outro.

EsperadoReal
libzoltan.solibtrilinos_zoltan.so
libpetsc.solibpetsc_real.so
libfoam_csr.solibfoam2csr.so
Correção: links simbólicos de compatibilidade numa pasta própria — zero mudança no sistema ou no OpenFOAM.

Caminho do CUDA fixo em versão antiga

-I/usr/local/cuda-11.6/include hardcoded no wrapper amgx4Foam.

Correção: trocado para /usr/local/cuda (symlink para a versão ativa).

MeshObject renomeado na v14

O OpenFOAM-14 substituiu MeshObject<Mesh,Tag,Type> por DemandDrivenMeshObject, com categorias de tag diferentes (TopoChangeableMeshObject exige 4 métodos virtuais puros que nossa classe não precisa).

Correção: migrado para DemandDrivenMeshObject com a tag DeletableMeshObject (sem virtuais puras — a classe só precisa ser recriada quando a malha muda).

Header removido na v14

cyclicAMILduInterface.H não existe mais — e não era de fato usado em nenhuma função.

Correção: #include removido.

thisDb() → db()

Método renomeado na interface lduMesh da v14.

Correção: substituído nas duas ocorrências.

PETSc nunca era inicializado

O foam2csr usa tipos do PETSc internamente, mas nada no caminho de execução chamava PetscInitialize — o código original dependia de outro componente (removido nesse fork) para isso.

Signal: Segmentation fault (11)
 #7 PetscVFPrintfDefault
 #8 AmgXSolver::setDeviceCount()
Correção: PetscInitializeNoArguments() guardado por PetscInitialized(), no construtor do contexto.

Residual history não gravado

O AMGX só permite consultar o resíduo após a solução se store_res_history estiver ligado — não estava no JSON de configuração inicial.

Correção: "store_res_history": 1 no config do solver principal.

MPI não inicializado em execução serial

Rodar icoFoam sem mpirun nunca inicializa o MPI — mas o AMGX chama funções MPI incondicionalmente.

Correção: não é bug, é requisito — essa classe de solver sempre roda via mpirun -np N icoFoam -parallel (N ≥ 2).

const-correctness

const double* passado onde a API do foam2csr espera PetscScalar* não-const.

Correção: const_cast<double*> no ponto de chamada (o valor não é de fato modificado).

Validação

Caso cavity (tampa móvel, solver icoFoam) — mesma malha, três configurações de compilador/solver.

BuildResíduo final de pResultado
GCC (CPU, DICPCG)8.638e-07referência
Intel oneAPI (CPU, DICPCG)8.638e-07idêntico ao GCC
AMGX (GPU, PCG+AMG)5.248e-19convergiu, campo final ~1e-4 do CPU

GCC e Intel produzem o campo de pressão bit-a-bit idêntico. GPU converge para a mesma física com uma diferença residual esperada — métodos iterativos diferentes (precondicionador por agregação vs. DIC), mesma tolerância alvo (1e-6).

Benchmark

Malha de 40.000 células (cavity, 100× mais fina que o tutorial padrão) — mede só o tempo de execução, não a qualidade do resultado.

CPU
2.3 s
GPU
6.4 s
10 passos de tempo. A CPU venceu aqui — nessa escala, o overhead de inicializar o contexto AMGX/CUDA a cada passo supera o ganho do solve em si. GPU só compensa com malhas bem maiores e com a estrutura do AMG reaproveitada entre iterações.

motorBike: 3,2 milhões de células

Aerodinâmica externa, foamRun com incompressibleFluid (SIMPLE, regime permanente). Tempo médio por iteração entre as iterações 10 e 100, 4 processos MPI.

GPU, 1ª tentativa
3,7 s
CPU, GAMG
2,55 s
GPU, tol. igualada
2,52 s
GPU, tol. + reuso AMG
2,48 s
A 1ª tentativa (8 processos) parecia 50% mais lenta, mas a causa era configuração: o amgx4Foam ignora o relTol 0.1 do fvSolution e a AMGX resolvia até a tolerância do JSON (1e-6), com 41 iterações por solve contra 2 do GAMG. Com a tolerância igualada, as três rodadas chegam ao mesmo Cd (0,720 a 0,721).

Por que a GPU só empata aqui. O solve de pressão na AMGX leva 0,26 s de cada iteração de 2,48 s, cerca de 10%. Os outros 90% são velocidade, turbulência, montagem das matrizes e pós-processamento, que continuam na CPU. Mesmo com um solve de pressão instantâneo, o ganho máximo seria de uns 12%.

A GPU tende a compensar quando a pressão domina a iteração: casos transientes (PISO/PIMPLE) com vários correctores e pFinal com relTol 0. É o perfil do motor com combustão do WiebePy, que é o próximo caso a medir.
